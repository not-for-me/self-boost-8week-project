## 배운 것

### 1. 현실의 PDF는 생각보다 지저분하다

**기대**: 증권사 리포트는 디지털 네이티브라 텍스트 추출이 쉬울 것

**현실**:
- 상당수 PDF가 **이미지 기반** (텍스트가 2x2 픽셀 이미지로 렌더링)
- pdfplumber로 텍스트 추출 → 빈 문자열 반환
- 표에 **테두리선이 없는 경우** 다수 → camelot(lattice/stream) 무용지물

```
pdfplumber: "텍스트가 있어야 표를 찾죠"  → 이미지 PDF에서 실패
camelot:    "선이 있어야 표를 찾죠"      → borderless 표에서 실패
docling:    "ML로 레이아웃을 분석합니다" → 둘 다 처리 가능
```

### 2. 앙상블보다 좋은 단일 모델이 낫다

처음 설계: pdfplumber + camelot + docling 앙상블로 recall 극대화

현실:
- pdfplumber, camelot은 실제 증권사 PDF에서 거의 작동 안 함
- docling 하나가 **borderless 표 + 이미지 PDF** 모두 처리
- 불필요한 복잡성만 증가시킨 셈

**교훈**: 이론적으로 완벽한 설계보다 **실제 데이터로 검증**이 먼저

### 3. OCR 키워드 변형 처리

OCR은 완벽하지 않다. 같은 지표도 다르게 인식됨:

```
원본: PER, PBR, PCR
OCR:  P/E, P/B, P/CF
```

해결: 키워드 목록에 OCR 변형 추가

```python
"valuation": {
    "keywords": [
        "PER", "PBR", "PCR",
        "P/E", "P/B", "P/CF",  # OCR variants
        "EPS", "BPS", "CFPS",
        "ROE", "ROA", "ROIC",
    ],
}
```

### 4. 병렬 처리의 트레이드오프

44개 PDF를 순차 처리하면 한참 걸림 → `ProcessPoolExecutor`로 병렬화

```python
with ProcessPoolExecutor(max_workers=4) as executor:
    futures = [executor.submit(process_pdf, pdf) for pdf in pdf_files]
```

**주의점**:
- 워커마다 Docling 모델을 새로 로드 → 메모리 사용량 증가
- 워커 수를 너무 늘리면 오히려 느려짐 (메모리 스왑)
- 적정 워커 수: CPU 코어 수 또는 그 이하

### 5. Suffix Array: "유사한 것끼리 모으기"

BPE 토크나이저는 텍스트에서 **가장 빈번한 문자열 패턴**을 찾아야 함. 모든 쌍을 비교하면 O(N²)이지만, Suffix Array를 쓰면 O(N)으로 가능.

**핵심 원리**: 사전순 정렬하면 공통 접두사를 가진 문자열들이 **이웃**하게 배치됨

```
"banana" → 정렬 후:
  a      ← 이웃끼리만 비교하면 됨
  ana    ← "a"로 시작하는 것들이 모임
  anana
  banana
  na     ← "na"로 시작하는 것들이 모임
  nana
```

### 6. LCP Array: "얼마나 똑같은지 재기"

**LCP (Longest Common Prefix)**: 정렬된 상태에서 이웃 간 공통 접두사 길이

- LCP 값이 높게 유지되는 구간 = **빈번하게 등장하는 긴 패턴**
- BPE가 병합할 후보를 찾는 데 활용

### 7. Kasai 알고리즘의 최적화 원리

**"이미 센 것은 다시 세지 않는다"**

```
banana와 bandana가 앞 3글자(ban) 같으면,
→ anana와 andana는 최소 2글자(an)는 무조건 같음
→ k를 0부터 세지 않고 k-1부터 시작
```

**SA와 Rank의 관계**:
- `SA[등수] = 원래_위치` (정렬 결과)
- `Rank[원래_위치] = 등수` (SA의 역함수)

Kasai가 원본 문자열 순서대로 훑으면서 LCP를 계산하므로, Rank로 "내 등수"를 찾고 `SA[Rank[i]-1]`로 "윗집"을 찾아 비교.

### 메모

#### 느낀 점: 현실과 이론의 간극

어제까지는 "Union-Find + Spatial Indexing으로 여러 탐지기 결과를 병합하면 완벽해!"라고 생각했다.

오늘 실제 PDF를 돌려보니:
1. pdfplumber는 이미지 PDF에서 무용지물
2. camelot은 borderless 표에서 무용지물
3. 결국 docling 하나만 살아남음

**"앙상블 아키텍처"라는 멋진 설계가 실제로는 docling 단독 실행과 다를 바 없었다.**

이론적으로 완벽한 설계보다 **실제 데이터로 빠르게 검증**하는 게 중요하다는 걸 체감했다. 처음부터 샘플 PDF 10개로 테스트했으면 시간을 아꼈을 것.

#### 남은 과제

Docling이 표 영역을 잘 찾는 건 확인됐다. 하지만:
- 찾은 표가 **재무제표**인지는 키워드 매칭에 의존
- 키워드 없는 표는 분류 불가
- **분류기 검증**이 다음 단계

#### 아키텍처 변경

```
Before (앙상블):
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ pdfplumber  │  │   camelot   │  │   docling   │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       └────────────────┼────────────────┘
                        ▼
              ┌─────────────────┐
              │ EnsembleDetector│  ← 복잡한 중복 제거
              │ (Union-Find)    │
              └─────────────────┘

After (단일):
              ┌─────────────────┐
              │ DoclingDetector │  ← ML 기반 + OCR 내장
              │ (force_ocr=True)│
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │ EnsembleDetector│  ← 단순 래퍼
              └─────────────────┘
```

복잡성은 줄고, 실제 작동하는 시스템이 됐다.
